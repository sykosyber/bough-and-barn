# Barn v0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build an executable Barn v0 reference runtime that licenses specialists from explicit work-state capability gaps, records every organizational mutation, exposes causal why-paths, and can optionally run logical agents through Qoder.

**Architecture:** A Python async domain kernel owns state transitions behind a `GraphStore` protocol. An in-memory store is the semantic oracle; Neo4j implements durable graph persistence. FastAPI exposes the kernel, a runtime adapter maps Barn agents to Qoder sessions, and a small web UI visualizes work/crew state.

**Tech Stack:** Python 3.11+, FastAPI, Pydantic v2, pytest/pytest-asyncio, Neo4j Python Driver 6.x, optional `qoder-agent-sdk`, vanilla browser JS/SVG for the first UI.

**Spec:** `docs/superpowers/specs/2026-09-12-barn-v0-design.md`

## Global Constraints

- Models never directly mutate the organization graph.
- Spawn requires explicit unresolved work capability need, no compatible reusable agent, and available budget.
- Events are append-only and commands are idempotent.
- Work resolution requires an artifact; verified work additionally requires passing verification.
- Keep OSAHR stochastic scheduling, GraphRAG, learned topology, and recursive native Qoder subagents out of v0.
- Qoder is a worker runtime; Barn owns logical agent identity and lifecycle.
