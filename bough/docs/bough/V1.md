# Staging, incrementality, Neo4j, speed

## Staging

| Mode | Key | bits n=3 | ontology copies=1 |
| --- | --- | --- | --- |
| `uniform` | situation signature | 8 | 8 |
| `derived` | enabled rule-id set | 2 (`{flip-on}`, `{}`) | 3 |
| `learned` | exact outgoing mass per rule_id | 2 on bits | descriptor only |

`learned` is not claim C4. C4 needs a pre-registered experiment. This mode is a lossless grouping of exact p-vectors so the descriptor exists before anyone advertises a learned stager.

## Incrementality

Witnesses already sit on automaton edges (`rule_id`, `match_id`, `bindings`).

- `refresh_probabilities` rematches each stored situation and reweights chance edges. No `RewriteEngine.apply`, no new nodes. If the `(rule_id, match_id)` set moved, refuse `STRUCTURAL_CHANGE`.
- `structural_rule_hits` uses kernel `RuleDependencySignature.compile` (public). An edit to `Route` / `Available` invalidates fail and repair.
- Failure and repair **rates are vertex attributes**. Editing them changes `G` and therefore the situation signature. That is not a same-node rate refresh.

`CompilationReport` carries `expand_seconds` and `refresh_seconds`. Those numbers compare two Bough paths. They are not a comparison with Gillespie.

## Neo4j

`bough.cypher.automaton_to_cypher` emits self-contained `MERGE` / `MATCH` statements. The expander never opens a driver. `NEO4J_URI` plus the optional `neo4j` package can push; absence is a no-op, not a refusal. Tests assert Cypher text.

## Speed claim in force

**None versus SSA.** Measure expand vs refresh. Report ratio. The standing warning from OSAHR's ontology probe remains: a correct overlay can be thousands of times slower than direct simulation. Bough's claim is exact jump-chain probabilities and an inspectable coalesced automaton.

C2 is the same kind of claim about *mass*, not time: `reach()` vs the three kernel schedulers on DAG families. See `docs/bough/C2.md`.
